# 供应链执行（演示）

被测系统代码 `supply-chain`，名称「供应链执行（演示）」。它是平台自带的示例被测系统，不是 TestAgent 本身。示例应用在 `examples/supply_chain`，本地地址 `http://127.0.0.1:8766`。

下面的需求正文以 `src/testagent/seed.py` 实际写入的 `raw_text` 为准。设计说明 `specs/test-agent-platform/design/nav-versioned-model-supply-chain-demo.md` 把 v1 / v2 的差异写在同一段里；种子按版本各存一句。

## 同一个系统，两个产品版本

v1.0 和 v2.0 是同一个被测系统下的两个版本，各有一份模型。后建的 v2.0 从 v1.0 复制模型后再扩展，改 v2 不会改 v1。

种子先把该版本的模型写完整（实体、字段、关系、动作和规则），再把固定需求挂上去，并带上指向模型节点、字段和关系的结构化引用。这是「系统已经按这个样子存在，再把需求补记到模型上」，不是先写需求再长出模型。

示例应用实现的是已经开发完成的 v2 规则（需要质检的物料必须质检合格才能过账，下达时供应商必须合格，收货受超收容差约束）。平台里的 v1.0 模型仍按 v1 规则描述。

### v1.0（在产）

申请 → 采购订单 → 收货过账即入库。

- 没有质检单，也没有「需要质检」。
- 没有超收容差。累计收货数量不得超过订购数量。
- 下达时供应商不得为冻结。

主流程：新建采购申请 → 提交 → 审批 → 按已批准申请创建采购订单 → 提交订单 → 审批订单 → 下达 → 按订单收货 → 收货过账，库存按收货数量增加 → 收齐后关闭。尚未收货的订单可以取消。供应商可以冻结，冻结后不得再新建或下达。

### v2.0（在 v1 上扩展）

复制 v1 的模型后增加：

- 质检单 `QualityInspection`，以及动作「创建质检单」「判定质检」。
- 物料字段 `inspectionRequired`（是否需要质检）。
- 采购订单字段 `overReceiveTolerancePct`（超收容差）。存的是小数，`0.1` 表示允许超收 10%。累计收货不得超过订购数量 ×（1 + 容差）。
- 下达时供应商必须为合格（`qualified`）。潜在供应商不能下达；冻结规则仍然适用。

主流程在「按订单收货」和「收货过账」之间多了质检：物料需要质检时，先创建质检单（待判定），再判定合格或不合格。合格才能过账；不合格不得入库。不需要质检的物料仍是草稿收货单直接过账。

## 固定需求

v1.0 写入 REQ-001～REQ-012，写完后标记为已封板：模型和需求只读，界面显示「已封板」。其他系统和其他版本不受影响。可以基于已封板的 v1.0 新建版本（v2.0 就是这样来的），新版本复制模型后仍可编辑。

v2.0 不重复未改动的 v1 需求。它只写入正文有变化的 REQ-007、REQ-008、REQ-009，以及仅 v2 的 REQ-013～REQ-016。

### 仅 v1.0 的正文

下面这些句子只写在 v1.0。v2.0 不再登记同编号需求。

**REQ-001 新建采购申请**  
采购员可为指定物料创建采购申请。数量必须大于 0，物料必须已存在。创建后申请处于草稿。

**REQ-002 提交采购申请**  
草稿状态的采购申请可由提交人提交，提交后进入待审批。数量仍须大于 0。

**REQ-003 审批采购申请**  
待审批的采购申请可由审批人批准或驳回。提交人不得审批自己提交的申请。批准后状态为已批准，驳回后为已驳回。

**REQ-004 按已批准申请创建采购订单**  
已批准的采购申请可转换成草稿采购订单，转换后申请状态为已转换，不得再次转换。若申请指定了供应商，该供应商不得为冻结。

**REQ-005 提交采购订单**  
草稿采购订单至少包含一行、金额大于 0 方可提交。若该供应商物料存在最小起订量，则行数量不得低于最小起订量。提交后进入待审批。

**REQ-006 审批采购订单**  
待审批的采购订单可由审批人批准或驳回。提交人不得审批自己提交的订单。

**REQ-010 关闭采购订单**  
已收货且各行在收货规则内已收齐的订单可以关闭。关闭后不得再收货。

**REQ-011 取消尚未收货的采购订单**  
草稿、待审批、已批准或已下达、且所有行累计收货数量为 0 的采购订单可以取消。已有收货的订单不得取消。取消后不得再收货。

**REQ-012 冻结供应商**  
可将供应商冻结。冻结后不得用该供应商新建或下达采购订单。已经下达且未取消的订单仍可继续收货、过账（按该版本的收货规则）。

### REQ-007 下达采购订单给供应商

v1.0：已批准的采购订单可下达给供应商。供应商不得为冻结。下达后订单为已下达，此后才允许收货。

v2.0：已批准的采购订单可下达给供应商。供应商必须为合格。下达后订单为已下达，此后才允许收货。

### REQ-008 按订单收货

v1.0：已下达或部分收货的订单可分次收货，收货数量必须大于 0。累计收货数量不得超过订购数量。已取消或已关闭的订单不得收货。收货后，若尚未收齐则为部分收货，收齐则为已收货。

v2.0：已下达或部分收货的订单可分次收货，收货数量必须大于 0。累计收货数量不得超过订购数量 ×（1 + 该订单超收容差）。已取消或已关闭的订单不得收货。收货后，若尚未收齐则为部分收货，收齐（在规则内）则为已收货。

### REQ-009 收货过账入库

v1.0：草稿收货单可过账，过账后对应仓库中该物料的在库数量按收货数量增加，库存不得变为负数。

v2.0：若物料需要质检，则须质检合格后方可过账入库；质检不合格不得入库。不需要质检的物料，草稿收货单可过账，过账后对应仓库中该物料的在库数量按收货数量增加，库存不得变为负数。

### 仅 v2.0

**REQ-013 物料质检要求**  
物料可标记为需要质检。需要质检的物料，其收货必须先创建质检单并给出合格或不合格结论，才能按 REQ-009 决定是否入库。

**REQ-014 创建质检单**  
未过账的收货单，若物料需要质检，可创建质检单，初始结论为待判定。

**REQ-015 判定质检**  
待判定的质检单可判定为合格或不合格。合格后方允许该收货单过账入库；不合格则该收货单不得过账入库。

**REQ-016 供应商准入**  
仅状态为合格的供应商可被下达采购订单。潜在供应商不能下达；冻结规则同时适用。

## 还原演示数据

`ops/restore_supply_chain.py` 只处理代码为 `supply-chain` 的这个系统。默认是演练，只打印计划，不改数据。`--apply` 会清掉该系统在平台里的业务数据（模型、接口、建议、版本、需求、策略、任务、用例、执行、缺陷、报告等），保留系统行和环境，然后按种子重建版本、模型和固定需求。

`--apply` 必须同时带 `--keep-repo` 或 `--repo-archive`。`--keep-repo` 不动本地测试仓；`--repo-archive <目录>` 把旧测试仓移到该目录（目录已存在则拒绝，不覆盖、不删除），再初始化一个空仓。

`--demo-url` 在重建之后向示例应用 `POST {url}/sample/reset`，清掉示例应用里的业务数据。不带这个参数就不会调用示例应用。

`ops/seed_supply_chain.py` 只在该系统还没有模型时写入一次。系统里已经有模型时它什么都不改。升级已有部署、需要换成当前种子时，用上面的还原脚本，不要只跑 seed。

`ops/reset_sut_data.py --sut <代码>` 可以把任意一个被测系统清到「只留系统行和环境」，默认也是演练。它不重建供应链演示。还原脚本在 `--apply` 时会用同一套清理，再调用种子。自己执行 `reset_sut_data.py --apply` 时同样要带 `--keep-repo` 或 `--repo-archive`。动手前先做数据库备份（`pg_dump`）；脚本本身不会替你备份。

不要删除 Docker 卷 `caddy-data`（里面是 HTTPS 证书）。还原演示数据不需要动任何卷。

### 本机（Windows）

仓库在 `D:\CodeWork\TestAgent\release\testagent`。示例应用端口是 **8766**。

```powershell
cd D:\CodeWork\TestAgent\release\testagent
uv run python ops/restore_supply_chain.py
uv run python ops/restore_supply_chain.py --apply --keep-repo --demo-url http://127.0.0.1:8766
```

第一行只演练。第二行改平台数据，并重置本机示例应用。示例应用需已在 `http://127.0.0.1:8766` 运行，否则 `--demo-url` 这一步会失败。

### 服务器（Docker，阿里云，目录 `~/testagent`）

在容器里用 `python`，不要在宿主机上用 `uv`。当前用户如果不能直接跑 Docker，在 `docker` 前加 `sudo`。

```bash
cd ~/testagent
git pull && docker compose up -d --build
docker compose exec testagent python ops/restore_supply_chain.py
docker compose exec testagent python ops/restore_supply_chain.py --apply --keep-repo --demo-url http://demo:8766
```

容器之间用服务名 `demo`，不是 `127.0.0.1`。平台容器里的 `TESTAGENT_DEMO_URL` 默认也是 `http://demo:8766`，但只有命令行带了 `--demo-url` 才会去调用示例应用的 `/sample/reset`。

`TESTAGENT_SEED_DEMO=1`（Compose 默认）只在启动时调用一次种子。种子发现该系统已经有模型就直接返回，不会替换旧数据。镜像升级之后，若要换成当前仓库里的已封板 v1.0（REQ-001～REQ-012）和只含增量需求的 v2.0（REQ-007～REQ-009、REQ-013～REQ-016），必须再跑上面的 `--apply`。
