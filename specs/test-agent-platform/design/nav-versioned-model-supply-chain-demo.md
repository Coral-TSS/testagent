# 导航调整、按版本建模，以及新的供应链演示系统

- 状态：已按 2026-11-21 反馈确定，实现中
- 基线：`develop` @ `f63211d`
- 范围：侧栏信息架构、模型归属到版本、用新的供应链演示替换旧采购演示。不改无关路线图项。

## 1. 侧栏：全部被测系统独立一级，建模回到当前系统里

### 1.1 现在的问题

当前「被测系统」是一组会变形的子菜单：未选系统时列出全部系统，点进一个系统后，左边整组菜单变成该系统的流程项，「全部被测系统」被挤到子菜单底部。建模又是另一组一级菜单，只是跟随当前系统。结果是：

- 系统列表和「进入某个系统后的工作菜单」混在同一个一级入口里，列表交互不清晰。
- 建模不在被测系统的流程菜单里，切系统、切项目别扭。
- 模型路由挂在系统上（`/suts/:sutId/model`），没有跟版本走。

### 1.2 新的信息架构

侧栏一级项目固定，**不要**在选中某个系统后，把「被测系统」整组替换成流程菜单。

一级顺序：

1. **全部被测系统**（独立一级，始终可点）→ `/suts` 系统列表。这是管理系统、进入某个系统的入口，不再把系统列表嵌在可变形的子菜单里。
2. **当前系统区**（仅当已经进入某个被测系统时显示，不是一个会把第 1 项吃掉的一级）：
   - 顶部是**当前系统切换**和**当前版本切换**，与顶栏选择器同步。从这里就能换系统、换版本，不必先退回列表。
   - 其下按工作流程排列，全部属于当前系统（及当前版本，若该页依赖版本）：
     - 概览 → `/suts/:sutId`
     - **建模**（子项，跟随当前版本，没有版本时禁用并提示「请先创建版本」）
       - 模型图谱
       - 模型评审
       - API 注册表
     - 版本与需求
     - 策略
     - 任务
     - 用例
     - 执行（带当前系统、版本筛选）
     - 缺陷（带当前系统、版本筛选）
3. **执行**、**缺陷**：继续保留跨系统的一级入口（不带系统参数，页内可筛选）。当前系统区里的同名项是当前系统范围。
4. **测试报告**：仍是跨系统一级。
5. 人员、Agent、用户：不变。

建模不再作为脱离系统和版本的全局一级菜单。未进入任何系统时，不显示「当前系统区」；从「全部被测系统」点进一个系统后，再出现该区。

其它已有约定保持：侧栏固定宽度、高亮按阶段、`/cases` 重定向、无版本时「版本与需求 / 策略 / 任务 / 建模」禁用、步骤条键不改。切换系统时尽量留在同一类页面；版本页因版本号不能沿用，回到新系统概览。切换版本时，若在版本、策略、任务或**建模**页，换到同一段的新版本。

更新 `specs/test-agent-platform/design/ux-navigation-and-panels.md` 中与本节冲突的部分。

## 2. 模型按版本管理

被测系统的每个版本都可以有自己的模型。老版本可能还在给客户使用，不能所有版本共用一份「系统级活模型」。

### 2.1 行为

- 建模（图谱、评审、API 注册表）一律针对**当前版本**。没有版本就不能建模。
- 查看或编辑 v1 的模型，不影响 v2；反之亦然。
- 新建版本时，默认从指定来源版本（缺省为最近一个版本）**复制**一份模型（节点、字段、链接、边、动作规则、API 绑定关系等），之后两边独立演化。第一个版本没有来源时，从空模型开始。
- 需求、策略、任务、用例、覆盖度本来就挂在版本上；范围计算、用例生成继续用该版本的模型与需求引用。
- 路由建议挂到版本，例如 `/versions/:versionId/model`、`/review`、`/apis`。旧的 `/suts/:sutId/model`（及评审、API）重定向到当前选中版本的对应页；没有版本则回到概览并提示先创建版本。

### 2.2 实现注意

请先核对现有库表：目前模型节点很可能是按 `sut_id` 存的，需求冻结时再快照。需要改成（或等效于）每个版本一份可编辑模型，而不是所有版本读写同一份活模型。迁移既有数据：每个已有版本得到一份属于自己的模型（可从当前系统模型复制），避免老版本打开后看到新模型。API 定义若仍按系统登记，版本模型里绑定的是该系统的 API；不要无故把 API 注册表做成完全孤立的另一套，但页面要在版本上下文中打开。具体表结构由实现时调查后决定，行为以本节为准。

## 3. 新演示系统：供应链执行

### 3.1 场景

准备一个新的被测系统，**删掉种子里的旧采购演示系统**（`procurement` / “Procurement approval (demo)”）。针对这个新系统提供可重复执行的**数据还原脚本**。

这套演示的设定是：被测系统本身已经开发完成，现在用 TestAgent 补需求、补测试，用来验证「AI 建模 + AI 设计用例」。因此：

- **代码和实体设计必须完整、稳定**，和下面写死的需求一致，不能再随手编需求。
- **种子里的初始模型，是「需求正式录入之前」就已经存在的系统模型**：实体、字段、动作、链接、状态、前置条件与效果都已按已开发系统登记好，但还没有需求引用。随后再写入下面这些固定需求，并挂上结构化引用。
- 演示业务数据保持少量即可，重点是**模型足够复杂**，能撑起范围计算、覆盖目标和跨需求端到端链路。
- 不必预置大量用例（可以没有，或最多一两例说明结构）；把「AI 设计用例」留给平台自己生成。
- 本次不要再埋故意的演示缺陷，也不要在用户可见文档里写旧采购演示的埋点缺陷。

系统中文名：**供应链执行（演示）**。系统代码：`supply-chain`。示例应用与 API 放到例如 `examples/supply_chain/`，替换对 `examples/procurement` 的演示依赖。字段名、实体名跟代码 / API 字段走，不跟数据库列名走。界面文案用简体中文。

### 3.2 两个版本（用来体现「模型跟版本走」）

- **v1.0**（在产客户版）：申请 → 订单 → 收货过账即入库。没有独立质检，也没有超收容差。
- **v2.0**（新版）：从 v1.0 的模型复制后再扩展——增加质检单、物料「需要质检」、收货超收容差、供应商必须为「合格」才能下达订单。v1.0 的模型保持不变。

种子顺序建议：先写入完整的 v2 领域所对应的「系统已开发完成」的代码与 API；再为 v1.0 登记初始模型（不含质检与容差）；写入 v1.0 的固定需求与引用；再创建 v2.0（复制 v1.0 模型并加上扩展），写入 v2.0 的固定需求与引用。还原脚本应能清掉该演示系统在平台里的数据以及示例应用里的业务数据，再按同一套逻辑重建，可重复执行。

### 3.3 实体、字段、状态、约束

分组建议：主数据、采购、仓储质检。

**物料 Material**

- 字段：`code`（必填）、`name`（必填）、`unit`（必填，枚举如 `PCS` / `KG` / `BOX`）、`inspectionRequired`（布尔，v1 模型可不登记或恒为否；v2 必有）、`safetyStock`（数值）
- 约束：编码唯一。

**供应商 Supplier**

- 字段：`code`（必填）、`name`（必填）、`status`（枚举：`potential` 潜在 / `qualified` 合格 / `frozen` 冻结）
- 状态：同上三个。
- 约束：冻结供应商不能用于新建或下达采购订单。

**供应商物料 SupplierMaterial**（供应商可供应的物料及其采购条件）

- 字段：`price`（必填，金额，必须大于 0）、`leadTimeDays`（整数，必须 ≥ 0）、`minOrderQty`（数值，必须大于 0）
- 链接：属于 Supplier，供应 Material。

**仓库 Warehouse**

- 字段：`code`（必填）、`name`（必填）

**库存 Inventory**

- 字段：`onHandQty`（数值，必须 ≥ 0）、`reservedQty`（数值，必须 ≥ 0）
- 约束：`onHandQty` 不得为负；`reservedQty` 不得超过 `onHandQty`。
- 链接：存放于 Warehouse，对应 Material。

**采购员 Buyer**

- 字段：`code`（必填）、`name`（必填）
- 约束：采购员不能审批自己提交的采购申请或采购订单。

**采购申请 PurchaseRequisition**

- 字段：`code`、`qty`（必须大于 0）、`needByDate`、`status`（枚举：`draft` / `submitted` / `approved` / `rejected` / `converted`）
- 状态：同上。
- 链接：申请物料 Material；可由 Buyer 提交；可选建议供应商 Supplier。

**采购订单 PurchaseOrder**

- 字段：`code`、`amount`（必须大于 0）、`currency`、`needByDate`、`status`（枚举：`draft` / `pending_approval` / `approved` / `issued` / `partial_received` / `received` / `closed` / `cancelled`）、`overReceiveTolerancePct`（数值，v2 才有，默认 0）
- 状态：同上。
- 约束：金额必须大于 0；已取消或已关闭的订单不能再收货或改数量。
- 链接：向 Supplier 采购；由 Buyer 提交/下达；可由已批准的 PurchaseRequisition 转换而来。

**采购订单行 PurchaseOrderLine**

- 字段：`orderedQty`（必须大于 0）、`receivedQty`（必须 ≥ 0）、`unitPrice`（必须大于 0）
- 约束：v1 下 `receivedQty` 不得超过 `orderedQty`；v2 下不得超过 `orderedQty * (1 + 订单超收容差)`。
- 链接：属于 PurchaseOrder；采购 Material。

**收货单 GoodsReceipt**

- 字段：`code`、`receivedQty`（必须大于 0）、`status`（枚举：`draft` / `posted`）
- 状态：同上。
- 链接：针对 PurchaseOrder / PurchaseOrderLine；收入 Warehouse；记录 Material。

**质检单 QualityInspection**（仅 v2.0）

- 字段：`code`、`result`（枚举：`pending` / `passed` / `failed`）、`defectQty`
- 状态：同上。
- 约束：`inspectionRequired = true` 的物料，质检未合格不得过账入库。
- 链接：针对 GoodsReceipt；检验 Material。

### 3.4 动作与业务链路

动作要有用途、输入输出、前置条件、效果，并绑定 API。链路由效果 → 下一动作的前置条件串起来，供第三阶段端到端生成使用。

**v1.0 与 v2.0 共有：**

| 动作 | 前置条件（摘要） | 效果（摘要） |
| --- | --- | --- |
| 新建采购申请 | 物料存在；数量 > 0 | 申请状态 = `draft` |
| 提交采购申请 | 状态 = `draft`；数量 > 0 | 状态 = `submitted` |
| 审批采购申请 | 状态 = `submitted`；审批人不是提交人 | 状态 = `approved` 或 `rejected` |
| 按申请创建采购订单 | 申请状态 = `approved`；若指定供应商则供应商不是 `frozen` | 生成草稿订单；申请状态 = `converted` |
| 提交采购订单 | 状态 = `draft`；至少一行；金额 > 0；各行数量 ≥ 对应 SupplierMaterial.minOrderQty（若有供应关系） | 状态 = `pending_approval` |
| 审批采购订单 | 状态 = `pending_approval`；审批人不是提交人 | 状态 = `approved` 或 `rejected` |
| 下达采购订单 | 状态 = `approved`；供应商状态 = `qualified`（v1 也可允许非冻结；v2 必须合格，见需求） | 状态 = `issued` |
| 按订单收货 | 订单为 `issued` 或 `partial_received`；收货数量 > 0；不超过允许上限（见行约束） | 生成收货单 `draft` 或直接待过账；回写行 `receivedQty`；订单进入 `partial_received` 或 `received` |
| 收货过账入库 | 见版本差异 | 收货单 = `posted`；对应库存 `onHandQty` 增加 |
| 关闭采购订单 | 状态 = `received`（各行已收齐，在容差规则内） | 状态 = `closed` |
| 取消采购订单 | 状态为 `draft` / `pending_approval` / `approved` / `issued`，且所有行 `receivedQty = 0` | 状态 = `cancelled` |
| 冻结供应商 | 供应商不是已冻结 | 状态 = `frozen` |
| 查询库存 | 物料与仓库存在 | 只读，不改状态 |

**收货过账入库的版本差异：**

- v1.0：收货单为 `draft` 即可过账，过账后直接增加库存。
- v2.0：若物料 `inspectionRequired = true`，必须已有结果为 `passed` 的质检单才能过账；`failed` 不得入库。不需质检的物料与 v1 相同。

**仅 v2.0：**

| 动作 | 前置条件 | 效果 |
| --- | --- | --- |
| 创建质检单 | 收货单存在且未过账；物料需要质检 | 质检结果 = `pending` |
| 判定质检 | 结果 = `pending` | 结果 = `passed` 或 `failed` |

主要端到端链路（v1）：新建申请 → 提交 → 审批通过 → 创建订单 → 提交 → 审批通过 → 下达 → 收货 → 过账入库 → 关闭订单。

v2 在「收货」与「过账入库」之间插入「创建质检单 → 判定通过」。

### 3.5 链接（双向）

至少包括：

- PurchaseRequisition 申请 Material
- PurchaseRequisition 由 Buyer 提交
- PurchaseRequisition 建议 Supplier（可选）
- PurchaseRequisition 转换成 PurchaseOrder
- PurchaseOrder 向 Supplier 采购（必填）
- PurchaseOrder 由 Buyer 负责
- PurchaseOrder 包含 PurchaseOrderLine
- PurchaseOrderLine 采购 Material
- SupplierMaterial 属于 Supplier，供应 Material
- GoodsReceipt 针对 PurchaseOrderLine，收入 Warehouse，记录 Material
- Inventory 存放于 Warehouse，对应 Material
- QualityInspection（仅 v2）针对 GoodsReceipt，检验 Material

### 3.6 固定需求（必须按此实现，不要改写成含糊的「用户可以……」）

编号固定。每条都要写入标题、正文，并挂上结构化引用（节点 / 字段 / 链接及角色）。v1.0 只挂 REQ-001～REQ-012；v2.0 在复制模型并扩展后挂 REQ-001～REQ-012 的对应项（按 v2 规则表述的版本，可用同一编号在 v2 重写差异句，或使用 REQ-001～REQ-012 加 REQ-013～REQ-016，但引用必须指向 v2 模型对象）。推荐：**两个版本都登记 REQ-001～REQ-012，其中与版本有关的句子按该版本模型写；v2 另增 REQ-013～REQ-016。**

**REQ-001 新建采购申请**  
采购员可为指定物料创建采购申请。数量必须大于 0，物料必须已存在。创建后申请处于草稿。

**REQ-002 提交采购申请**  
草稿状态的采购申请可由提交人提交，提交后进入待审批。数量仍须大于 0。

**REQ-003 审批采购申请**  
待审批的采购申请可由审批人批准或驳回。提交人不得审批自己提交的申请。批准后状态为已批准，驳回后为已驳回。

**REQ-004 按已批准申请创建采购订单**  
已批准的采购申请可转换成草稿采购订单，转换后申请状态为已转换，不得再次转换。若申请指定了供应商，该供应商不得为冻结。

**REQ-005 提交采购订单**  
草稿采购订单至少包含一行、金额大于 0 方可提交。若该供应商物料存在最小起订量，则行数量不得低于最小起订量。提交后进入待审批。

**REQ-006 审批采购订单**  
待审批的采购订单可由审批人批准或驳回。提交人不得审批自己提交的订单。

**REQ-007 下达采购订单给供应商**  
已批准的采购订单可下达给供应商。v1.0：供应商不得为冻结。v2.0：供应商必须为合格。下达后订单为已下达，此后才允许收货。

**REQ-008 按订单收货**  
已下达或部分收货的订单可分次收货，收货数量必须大于 0。v1.0：累计收货数量不得超过订购数量。v2.0：累计收货数量不得超过订购数量 ×（1 + 该订单超收容差）。已取消或已关闭的订单不得收货。收货后，若尚未收齐则为部分收货，收齐（在规则内）则为已收货。

**REQ-009 收货过账入库**  
v1.0：草稿收货单可过账，过账后对应仓库中该物料的在库数量按收货数量增加，库存不得变为负数。v2.0：若物料需要质检，则须质检合格后方可过账入库；质检不合格不得入库。不需要质检的物料与 v1.0 相同。

**REQ-010 关闭采购订单**  
已收货且各行在收货规则内已收齐的订单可以关闭。关闭后不得再收货。

**REQ-011 取消尚未收货的采购订单**  
草稿、待审批、已批准或已下达、且所有行累计收货数量为 0 的采购订单可以取消。已有收货的订单不得取消。取消后不得再收货。

**REQ-012 冻结供应商**  
可将供应商冻结。冻结后不得用该供应商新建或下达采购订单。已经下达且未取消的订单仍可继续收货、过账（按该版本的收货规则）。

**REQ-013（仅 v2.0）物料质检要求**  
物料可标记为需要质检。需要质检的物料，其收货必须先创建质检单并给出合格或不合格结论，才能按 REQ-009 决定是否入库。

**REQ-014（仅 v2.0）创建质检单**  
未过账的收货单，若物料需要质检，可创建质检单，初始结论为待判定。

**REQ-015（仅 v2.0）判定质检**  
待判定的质检单可判定为合格或不合格。合格后方允许该收货单过账入库；不合格则该收货单不得过账入库。

**REQ-016（仅 v2.0）供应商准入**  
仅状态为合格的供应商可被下达采购订单。潜在供应商不能下达；冻结规则同时适用。

### 3.7 少量演示数据

示例应用里只准备能跑通主链路的少量数据，例如：

- 物料 3 个：普通件（不需质检）、需质检件（v2 用）、大宗件（单位 KG）。
- 供应商 2 个：一个合格，一个潜在或冻结。
- 供应商物料：合格供应商对前两种物料有价格、交期和最小起订量。
- 仓库 1 个；库存各物料少量在库。
- 采购员 2 个（以便「不能审自己」）。
- 单据不必很多：可有一张草稿申请、一张待审批订单，便于打开界面，但不是必须堆满历史单。
