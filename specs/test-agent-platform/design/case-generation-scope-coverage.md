# 用例生成：按需求圈定本体范围与覆盖度校验

- 状态：已评审（2026-11-21），按决议实现中
- 日期：2026-11-21
- 对应代码：从 `develop` @ `399ba55` 起实现
- 相关实现：`src/testagent/services/case_gen.py`、`src/testagent/agent/tools.py`、`src/testagent/services/cases.py`

本文讨论「按需求生成用例」时，如何把本体模型交给大模型、以及如何保证覆盖全。跨需求的端到端用例放在第三阶段，在第一、二阶段完成后再做。三个阶段均已批准实现。

---

## 1. 要解决的问题

现在的生成入口是一个版本下的一组需求。每条需求至少要写出正常、边界、异常三条用例，并挂上需求编号、模型节点和实体字段。这一点要保留。

但模型披露方式有两个缺陷：

1. **提示词里直接塞摘要**。生成时会把本系统的动作摘要、关系摘要、API 摘要整份写入提示词（动作和 API 各最多 40 条，描述截到 300 字）。系统稍大就会被截断，上下文里一定有缺失；系统不大时，又会塞进大量与当前需求无关的内容。
2. **覆盖靠大模型自觉**。校验只检查：需求编号是否属于本次目标、节点和字段 ID 是否存在、请求体字段是否符合 API 定义、每条需求是否至少 3 条用例。平台已有节点和字段覆盖度，但生成结束后并没有拿它当验收门槛。需求正文也不在提示词里，要靠大模型自己去查。

结果是：测不全和测跑偏都可能发生，而且事后不容易区分「模型里没有」「提示词被截掉了」还是「大模型没去查」。

目标改成一句话：**用代码确定性地圈出范围并定好覆盖目标，让大模型在范围内用工具查细节，最后用校验强制覆盖全。**

---

## 2. 本体现在怎么存、现在怎么交给大模型

### 2.1 存储

本体存在 PostgreSQL 的关系表里，没有用图数据库，也没有用 RDF。和 Palantir 一样，核心构件是对象、属性、链接、动作：

| 构件 | 我们的表 / 字段 | 说明 |
| --- | --- | --- |
| 对象 | `model_node`（`kind = entity`） | 实体。状态、约束目前还在 `attributes` JSON 里。 |
| 属性 | `entity_attribute` | 字段：类型、是否必填、格式、枚举、示例、引用的实体。 |
| 链接 | `model_link` | 双向读法、基数、是否必填、外键字段，多对多可走中间实体。这是主路径。 |
| 动作 | `model_node`（`kind = action`） | 用途、输入输出、前置条件（`preconditions`）、效果（`effects`），以及绑定的 API（`node_api_link`）。 |
| 图上的边 | `model_edge` | 角色：`source` / `target`（历史关系节点两端）、`actor` / `object`（动作与实体）、`ref`（只读引用）。 |

需求通过三张表引用本体，且带角色（`actor` / `condition` / `action` / `result` / `constraint`）：

- `requirement_node_link`：引用实体或动作
- `requirement_attribute_link`：引用 `实体.字段`
- `requirement_link_ref`：引用链接（例如「付款支付采购订单」）

用例通过 `case_requirement_link`、`case_node_link`、`case_attribute_link` 回指需求和本体。版本上已有 `coverage_report`。

### 2.2 当前披露方式

`CaseGenerationService.generate()` 调用 `generate_cases` 时，提示词输入包括：

- `requirement_codes`、`requirements`（只含 id / code / title，不含正文和结构化引用）
- `actions` = `action_summaries()`（最多 40）
- `links` = `link_summaries()`
- `apis` = `api_summaries()`（最多 40）

大模型还可以调用：`list_requirements`、`get_requirement`、`list_nodes`、`get_node`、`search_nodes`、`list_fields`、`list_links`、`list_apis`、`get_api_schema`、`list_cases`、`search_memory`。这些工具当前面向整个被测系统，没有「本次需求范围」的边界。

## 3. 和 Palantir 的对照

思路上接近，职责不同。

相同点：

- 本体都由对象、属性、链接、动作构成；我们的 `model_link` 本来就是按这个模型设计的。
- 都不会把整份本体塞进提示词，而是把本体做成工具：大模型按需查询对象和链接，或查看动作的参数与规则。
- 工具能看见什么，由范围决定。Palantir 用权限和对象集；我们用「本条需求圈定的范围清单」。

不同点：

- Palantir 的本体接的是真实业务数据。大模型查到的是具体的订单、供应商，并通过动作改变真实数据。我们的本体描述的是系统**应该怎么运转**，大模型查的是规则，用来推导测试，并不执行这些动作。
- Palantir 的动作带有严格的参数校验和提交规则。我们的前置条件和效果目前只用来推导测试点；改完之后，校验的是「生成的用例有没有覆盖这些规则」，而不是动作有没有真的执行成功。
- 我们多出来的一块是**覆盖度校验**：范围里的每一项都必须被用例覆盖，或者由人（或大模型附议、人确认）写明不覆盖的理由。这是测试场景特有的，Palantir 没有这个概念。

所以改完之后，披露方式会更像 Palantir 的「本体即工具」；但范围计算、覆盖门槛、以及后面的端到端链路，是测试平台自己的部分。

## 4. 总体流程

按需求逐条（也可一次传入多条，但范围按需求分别计算，避免串味）：

1. **代码计算范围**。从该需求已引用的节点、字段、链接出发，按第 5 节的深度规则向外扩展，得到一份范围清单：对象 ID、名称，以及每项必须覆盖什么。
2. **范围预览（第二阶段起为必经步骤）**。生成前必须让测试人员看到将纳入的对象和覆盖目标，和他们在测试设计里看覆盖情况一样。人可以增删清单中的项、调整深度后再算一遍，确认后才生成。第一阶段后端先提供计算并返回清单的接口，可用默认清单跑通生成；第二阶段把预览变成门禁，未确认不得生成。
3. **提示词只放清单，不放摘要全文**。需求编号、标题，以及范围清单（ID、名称、覆盖目标）。正文、字段类型、枚举、API 格式等一律不预先塞入。
4. **大模型按清单用工具查细节**。工具只能返回清单内的数据；查范围外的对象返回明确错误，而不是空结果。每次运行记录查过哪些项。
5. **生成后校验**。除现有的 ID / 请求体 / 「每条需求至少 3 条」之外，对照清单检查覆盖目标。未覆盖且没有有效放弃理由的，自动打回重写，机制与现在校验失败重试相同。
6. **写入用例和覆盖报告**。评审时可看到：覆盖了哪些目标、哪些是放弃、大模型查过哪些项。

## 5. 影响范围深度（已于 2026-11-21 拍板）

浅了会测不全，深了会测太多。规则必须是确定性的：同样的需求、同样的模型、同样的深度，得到同一份清单。深度可由全局默认，也可按需求覆盖。下列默认值与走边规则以第 12 节决议为准。

### 5.1 术语

- **种子（深度 0）**：需求已经显式引用的对象。只来自 `requirement_node_link`、`requirement_attribute_link`、`requirement_link_ref`，再加上这些字段所属的实体（字段不能脱离实体存在）。
- **扩展一层**：从当前已入选的对象出发，沿下面列出的边再走一步。默认深度为 1，即「种子 + 向外一层」。
- **远侧实体**：一条链接的另一端。例如「采购订单属于供应商」中，若种子是采购订单，供应商就是远侧实体。

### 5.2 默认深度：1（全局默认，已确认）

从种子出发，只走下面这些边，并且只走一步：

**从字段出发**

- 纳入所属实体（若还没有）。
- 纳入输入、输出、前置条件或效果里提到该字段的动作。
- 若该字段是某条链接的外键，纳入这条链接。

**从实体出发**

- **纳入该实体的全部已登记字段**（`entity_attribute` 中的行，不限于必填）。需求常常不会把字段一一写全，但字段仍是必要测试点。只引用了实体、没有引用任何字段时，同样把该实体的全部已登记字段纳入覆盖目标。人若认为某字段与本需求无关，在预览里去掉即可。
- 纳入以该实体为 `actor` 或 `object` 的动作（不沿 `ref` 边走）。
- **纳入与该实体任一端相连的链接，无论是否必填。** 远侧实体进入清单，但不再从远侧继续往外跳（见 5.3）。链接是双向的，因此「采购订单属于供应商」和「付款支付采购订单」在采购订单入选后都会进入清单。
- 纳入该实体上、被已纳入动作用到的状态（例如前置条件里的 `pending_approval`）。不自动把实体上每一个状态都变成覆盖目标。

**从动作出发**

- 纳入绑定的 API。
- 纳入全部前置条件和全部效果里提到的实体、字段、状态、链接。
- 纳入输入输出里绑定到 `实体.字段` 的那些字段。
- 纳入 `actor` / `object` 边指向的实体。

**从链接出发**

- 纳入两端实体（远侧实体进入清单，但默认不再从远侧继续往外跳，见 5.3）。
- 纳入外键字段、是否必填、基数。这些会生成对应的覆盖目标。

### 5.3 明确不走的边

这些边在深度 1 下都不走；深度 2 也不建议自动走，除非人在预览里手动加入：

1. **`ref` 边**。只读引用，不表示这条需求要行使该对象。
2. **从远侧实体再向外的链接和动作**。深度 1 会纳入与已入选实体相连的链接（含非必填），远侧实体因此进入清单，也纳入该远侧实体的已登记字段；但不会再从远侧展开它的其它链接、其它动作。例如审批需求会纳入「采购订单属于供应商」和供应商实体及其字段，但不会再纳入供应商的其它关系或动作。
3. **不再把「实体上未被需求点名的字段」列为不走边。** 已纳入实体的全部已登记字段都是覆盖目标。未在 `entity_attribute` 登记、只存在于旧 `data_schema` / `attributes` JSON 里的项，不自动变成覆盖目标，直到字段被正式登记。
4. **只读查询类动作**（例如「列出付款」）。仅当需求直接引用了它，或它被标成该需求的 `result`（用来断言），才纳入。否则深度 1 不自动带上。
5. **下游动作**。某动作的效果使实体进入状态 S，另一个动作的前置条件是状态 S——这已经是一条业务链路。默认不沿这条链路自动纳入下一个动作，否则单条「审批」需求会把「登记付款」一并生成出来。这类链路留给第三阶段的端到端用例。

### 5.4 深度 0 和深度 2

- **深度 0**：只用种子，不做扩展。适合需求引用已经非常完整的情况。风险是：引用漏了动作或前置条件时，会测不全。
- **深度 2**：在深度 1 的结果上再走一层，且**仍然遵守 5.3**（尤其是不自动纳入下游动作、不从远侧继续跳）。因为字段和非必填链接已在深度 1 纳入，深度 2 主要多纳入的是：从深度 1 新进入的邻近对象再往外看到的、仍被 5.3 允许的项。容易偏多，建议只作为某条需求的覆盖项，不作为全局默认。

不提供「沿状态迁移一直走下去」的自动深度。那是端到端，不是单条需求的范围。

### 5.5 用演示系统举例

演示系统（`procurement`）里现有：

- 实体：`PurchaseOrder`（状态：`draft`、`pending_approval`、`approved`、`rejected`、`paid`；约束：金额必须大于 0）、`Supplier`、`Approver`（约束：审批人不能审批自己提交的订单）、`Payment`（约束：付款合计不能超过订单金额）。
- 动作：`Create purchase order`（对象为采购订单，条件为金额大于 0）、`Approve purchase order`（审批人 → 采购订单，条件为订单处于待审批）、`Record payment`（对象为付款，条件为订单已批准）、`List payments`（对象为付款）。
- 链接：采购订单属于供应商（多对一）；付款支付采购订单（多对一）。

假设有一条需求：「待审批的采购订单可由审批人批准或驳回；提交人不得审批自己的订单。」并已引用动作「批准采购订单」、实体 `Approver`、字段 `PurchaseOrder.status`。

在**深度 1**下，清单大致是：

- 纳入：动作「批准采购订单」及其 API、前置条件（订单为 `pending_approval`）、效果（状态变为 `approved` 或 `rejected`）、审批人不能审自己的约束、实体 `PurchaseOrder` 与 `Approver`，以及这两个实体上全部已登记字段（不限于已被需求引用的 `status`）。
- 同时纳入与这些实体相连的链接，无论是否必填：例如「采购订单属于供应商」、「付款支付采购订单」。远侧实体 `Supplier`、`Payment` 进入清单，并纳入它们的已登记字段；但不再从供应商或付款展开其它链接，也不自动纳入它们的动作。
- 不纳入：`Create purchase order`（上游动作）、`Record payment`（下游动作）、`List payments`（只读查询）。即使付款实体因链接进入清单，也不把这两个动作带进来。
- 覆盖目标示例：前置条件满足时的批准、前置条件满足时的驳回、订单不是待审批时应当拒绝、审批人审批自己的订单应当拒绝、效果中两个目标状态都要断言到；再加上已纳入实体的各字段测试点，以及上述两条链接的外键 / 基数相关目标。
- 若测试人员认为付款或供应商与本条审批需求无关，在预览里去掉即可。这正是预览要拦住「测太多」的地方。

如果把深度改成 2，并且误把「下游动作」也打开，就会把「登记付款」一并生成进来——这对「审批」这条需求来说通常过深。这正是预览步骤要拦住的情况。

### 5.6 需求几乎没有结构化引用时

如果需求只有标题和正文，没有挂节点、字段、链接，代码算不出有意义的种子。决议：

- **必须先补上结构化引用才能生成。** 本体被用起来才有价值，缺引用就拦截并明确提示，而不是降级生成。
- 不退回到今天这种「把全系统摘要塞进提示词、让大模型自己在全图里找」的方式。那会把第 1、2 节的问题重新引入。
- 根据正文做一次只读的引用建议，仍可作为后续增强：必须由人确认后写入那三张引用表，再进入范围计算。第一、二阶段可以先不做建议，但缺引用时必须拦截。

### 5.7 深度的配置与预览

- 全局默认深度：1。
- 单条需求可覆盖为 0、1、2。
- 生成前展示范围预览：列出将纳入的实体、字段、动作、链接、API，以及每项覆盖目标；标明每一项是种子、扩展，还是人手动加入。
- 人可以：去掉某项、手动加入范围外的对象、改深度后重新计算。手动加入的项同样产生覆盖目标，除非人同时标为「仅供参考、不作为覆盖门槛」。
- 预览确认后的清单随这次生成运行一并保存，便于事后对照。

## 6. 范围清单与提示词

清单是短结构，只放 ID、名称、类型和覆盖目标，不放类型定义、枚举值、API 请求体、长描述。大致形状：

```json
{
  "requirement": {"code": "REQ-00X", "title": "……"},
  "depth": 1,
  "nodes": [
    {"id": "…", "kind": "action", "name": "Approve purchase order", "origin": "seed"}
  ],
  "fields": [
    {"id": "…", "entity": "PurchaseOrder", "name": "status", "origin": "seed"}
  ],
  "links": [],
  "apis": [
    {"id": "…", "method": "POST", "path": "/sample/orders/{order_id}/decision"}
  ],
  "targets": [
    {"id": "t1", "type": "precondition_met", "action": "Approve purchase order", "when": "PurchaseOrder.status == pending_approval"},
    {"id": "t2", "type": "precondition_violated", "action": "Approve purchase order", "when": "status 不是 pending_approval"},
    {"id": "t3", "type": "effect", "action": "Approve purchase order", "then": "status → approved"},
    {"id": "t4", "type": "effect", "action": "Approve purchase order", "then": "status → rejected"},
    {"id": "t5", "type": "constraint", "text": "审批人不能审批自己提交的订单"}
  ]
}
```

覆盖目标的主要类型：

- 已纳入实体的全部已登记字段：至少有一条用例真正用到它（`attribute_ids` 中出现）。人在预览里去掉的字段不再作为门槛。
- 已纳入动作：前置条件满足（正常）、每条前置条件至少有一次被违反（异常）。
- 已纳入动作的每条效果：都要在预期结果里断言。
- 已纳入的链接（含非必填）：外键缺失、指向不存在对象；按基数补充 1:1 已被占用、1:N / M:N 多对象等边界（与现有生成说明一致，但只针对清单内的链接）。非必填链接的「缺失」类目标以可空为前提，不要写成必填校验。
- 已纳入的约束。
- 已纳入 API：步骤里的请求体必须符合 schema（沿用现有校验）。

提示词只保留清单和生成规则（每条需求至少正常 / 边界 / 异常三条、类别、不要把 scenario 写成 type_tag 等）。不再写入 `action_summaries` / `link_summaries` / `api_summaries`。需求正文通过 `get_requirement` 获取，该工具需同时返回结构化引用。

## 7. 工具：范围之内、查不到要说清楚、留下痕迹

第一阶段就要改工具边界，不然大模型仍可能在全系统里漫游，清单就失去意义。

- 本次运行绑定一份范围。`list_*` 只列出清单内的对象；`get_node` / `get_api_schema` / `list_fields` 等查询范围外 ID 时，返回明确错误（例如「不在本次需求范围内」），不得返回空对象或静默成功。
- `list_cases` 仍可用于避免重复，但默认只返回与本需求或本范围节点相关的已有用例。
- `search_nodes` 同样不得搜出范围外的节点。
- 每次工具调用记入这次 `agent_run` 的步骤：查了哪个 ID、命中还是越界。评审和排错时可以回答「它没看到什么」。
- 工具本身要对准数据：前置条件、效果、字段类型和枚举、API schema 必须与库中一致，不能再经过一层易过期的摘要截断。

---

## 8. 覆盖度校验

生成结果先过现有校验（需求编号、节点和字段 ID 属于本系统、请求体符合 API、每条需求至少 3 条用例），再过清单校验：

- 每个覆盖目标要么被至少一条新用例命中，要么带有放弃理由（`waiver`：目标 ID、理由、提出者是 agent 还是人）。
- 大模型提出的放弃，生成时可以先记下来，但**不能**单独用来通过门槛，必须由人确认后才算覆盖。第一阶段若还没有确认界面，把未覆盖项直接打回，不接受自动放弃。第二阶段提供确认流程。
- 未通过则重试，次数与现有 `generate_cases` 校验失败重试相同。
- 通过后写入覆盖报告：按需求列出目标、命中的用例、放弃项。现有的节点 / 字段覆盖度继续保留，并增加「按需求 × 覆盖目标」这一层，供评审查看。

「命中」的判定要写死，不能靠读用例标题：

- 字段目标：用例的 `attribute_ids` 包含该字段。
- 动作 / 节点目标：用例的 `node_ids` 包含该动作。
- 前置条件 / 效果 / 约束：用例输出里要显式引用目标 ID（例如 `covers: ["t1", "t3"]`）。这样校验是确定性的。若某条用例声称覆盖某目标，但没挂上对应节点或字段，仍判为未命中。

---

## 9. 数据模型、接口和界面（建议）

尽量少加表，能放进现有 JSON 的先放进运行记录。

- **范围快照**：随 `agent_run.input_refs` 或单独一张 `case_gen_scope` 表保存（版本、需求、深度、清单全文、人是否改过）。预览确认和最终生成共用这份快照。
- **放弃项**：可放在覆盖报告的 `content` 里，或 `coverage_waiver`（目标、理由、确认人、时间）。人确认过的放弃，在模型和需求引用未变时，重新生成可以默认带上。
- **需求级深度**：需求的 `structured` 或单独列 `scope_depth`。未设置则用全局默认。
- **全局默认**：放进现有 Agent / 系统设置，默认值为 1。

接口建议：

- `POST /versions/{id}/case-gen/scope`：按需求计算清单，不调用大模型。
- `PUT /versions/{id}/case-gen/scope`：保存人的增删和深度。
- `POST /versions/{id}/cases/generate`：只接受已确认的清单；不再在服务端即时重算后直接覆盖人的修改。

界面：在用例生成前增加「范围预览」一步（可做在版本页或用例页）。用表格列出纳入项和覆盖目标，提供深度切换、增删、确认后生成。评审用例时能看到覆盖矩阵和工具查询记录。

兼容性：旧的生成接口保留，但行为改为「先算范围再生成」。第一阶段可以用算出的默认清单直接生成（便于先改后端并跑通测试）；第二阶段起，预览确认为必经一步，未确认不得生成。不再向提示词注入 40 条摘要，属于预期的破坏性变化，需在变更记录里写明。

---

## 10. 分阶段

**第一阶段（范围 + 工具，先做）**

- 实现范围计算（默认深度 1，规则按第 5 节及第 12 节决议）。
- 提示词改为只放清单；去掉摘要注入。
- 工具绑定范围，越界返回明确错误，并记录查询。
- `get_requirement` 返回正文和结构化引用。
- 单测：用演示系统的模型固定几条需求引用，断言清单的纳入与排除（特别是：实体字段全部纳入、非必填链接纳入但远侧不再跳、下游动作和只读查询不纳入）。
- 这一阶段可以先不拦「人确认预览」，用默认清单跑通生成，但接口必须能返回清单。缺引用时即应拦截，不降级到全系统摘要。

**第二阶段（校验门槛 + 预览 + 深度配置）**

- 覆盖目标生成与生成后校验、失败重试。
- 范围预览界面和深度配置；预览为生成前的必经步骤，确认后才生成。
- 放弃理由必须由人确认，以及覆盖矩阵展示。
- 需求缺少引用时的拦截与提示。

**第三阶段（端到端，第一、二阶段完成后再做，现已批准实现）**

- 用动作的「效果 → 另一动作的前置条件」串出跨需求链路，例如创建订单 → 审批 → 登记付款。
- 链路由代码从状态迁移推出，再交给大模型写成跨需求用例。
- 用例挂在版本或策略层，关联途经的多条需求。
- 覆盖度增加链路和状态迁移两个维度。
- 与单条需求的深度规则分开，避免把端到端重新塞回「把深度调大」。

## 11. 测试计划（实现时）

- 范围计算：纯函数单测，覆盖 5.5 的例子和 5.3 的每条不走边（含字段全纳入、非必填链接纳入但远侧不展开）。
- 工具越界：范围内成功、范围外明确报错、查询写入运行记录。
- 提示词：断言不再包含全量 `actions` / `apis` 摘要，且包含清单。
- 覆盖校验：缺目标则失败；补 `covers` 与节点、字段后通过；未确认的放弃不能通过。
- 回归：现有 `generate_cases` 的结构校验、API 请求体校验、每条需求至少 3 条，仍然有效。
- 前端（第二阶段）：预览的增删、改深度后重算、确认后才调用生成；缺引用时拦截。
- 端到端（第三阶段）：用演示系统断言能推出「创建 → 审批 → 登记付款」链路，生成的跨需求用例挂到途经需求，且不会把下游动作重新并进单条需求的深度 1 清单。

## 12. 评审决议（2026-11-21）

1. **全局默认深度定为 1。** 5.3 中「不自动纳入下游动作、不从远侧再跳、不自动纳入只读查询」保持不变。字段与非必填链接按下面 2、3 条调整。
2. **需求只引用了实体、没有引用字段时，仍纳入该实体的全部已登记字段作为覆盖目标。** 需求没写到的字段，测试点仍然有必要。不限于必填字段。人可在预览里去掉无关项。
3. **非必填链接在深度 1 也纳入，只是不从远侧再展开。** 远侧实体及其已登记字段进入清单，但不再展开远侧的其它链接和动作。
4. **预览是必要的。** 至少让测试人员在生成前预见覆盖情况，和他们在测试设计中看覆盖一样。第二阶段起，预览确认为必经步骤；第一阶段可用默认清单先跑通后端。
5. **没有结构化引用就不能生成。** 本体被用起来才有价值；必须先补引用。不退回把全系统摘要塞进提示词的老办法。根据正文建议引用可作为后续增强，但仍需人确认后写入引用表。
6. **大模型提出的放弃必须由人确认，才能算作覆盖。**

实现按第 10 节的阶段 1、2、3 依次进行，第三阶段一并实现。
