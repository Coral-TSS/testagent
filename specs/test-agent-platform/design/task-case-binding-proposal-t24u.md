## 3 根因

1. **策略和用例是两条平行的链**：`StrategyService.generate` 让模型按需求“分组成任务”，输出 `TaskDraft(name, kind, requirement_codes, description)`；代码只写 `test_task` 和 `requirement_ids`，从不查询或创建用例（`services/strategy.py`）。用例生成（`case_gen`）也不知道任务。两边唯一的交点是人工“用例与定时”页。
2. **任务的分类只有两种**：`kind ∈ {requirement, regression}`，模型只能把“幂等”“重置可重复性”归到需求测试；`type_tag`（functional/boundary/…）是用例级标签，任务级没有“质量属性”这一维。
3. **执行器按 `type_tag` 白名单跳过**：`select_executor` 只执行 `functional`/`api`，`boundary` 被当成“非功能”。但边界值是功能测试的一种设计方法，不是性能/安全这类非功能类型——这是一个独立的 bug，任务打通后会更明显（更多边界用例进任务、却被跳过）。
4. **任务描述 ≈ 用例提纲**：策略提示词要求“写清楚测什么”，模型就把用例级的步骤写进了任务描述，看上去像“任务里应该有用例”，但没有落地。

## 4 推荐设计

### 4.1 任务只引用用例，不创建用例

- 用例是唯一的测试资产（可审阅、修订、自动化、复用到回归）；任务是“这次跑哪些用例、用什么执行者、在什么环境、何时跑”。
- 任务不再生成“自己的”用例。AI 生成策略时：
  1. 先按选择规则从已有用例里挑（见 4.2）；
  2. 如果某个需求/质量属性一个用例都没有，就在策略结果里列出“缺口”，提供按钮“为缺口生成用例”（调用现有 `generate_cases`，生成草稿，人审后可执行，然后自动进入匹配的任务）。
- 这样“任务里看不到用例”的问题变成：任务创建即带用例；缺口一目了然。

### 4.2 任务的用例选择规则（动态 + 手工）

任务增加 `selector`（JSON）：

| 字段 | 例子 | 说明 |
|---|---|---|
| `requirement_ids` | REQ-001 | 关联这些需求的用例 |
| `categories` | `requirement` / `quality` / `regression` | 见 4.3 |
| `type_tags` | functional, api, boundary | 用例类型 |
| `scenarios` | normal, boundary, exception | 场景 |
| `priorities` | P0, P1 | 冒烟可只选 P0 |
| `quality_tags` | idempotency, concurrency, reset | 质量属性（4.3） |
| `status` | 默认 ready | 只选可执行用例 |

- `task_case` 继续保存“实际要跑的清单”，每行加 `source = rule | manual`，人工加入/移出的优先，规则再次同步时不覆盖人工结果。
- 新用例变为可执行时（`case.ready` 事件），自动加入规则匹配的、未归档且未在运行的任务；任务页显示“规则匹配 N 个，已手工加入 M 个，手工排除 K 个”，可“立即同步”。
- 本次已上线的“用例清单 → 批量加入任务”就是手工加入的入口。

### 4.3 任务分类

| 分类 | 含义 | 例子（本示例系统） |
|---|---|---|
| 需求验证 `requirement` | 一条需求的业务规则：正常/边界/异常，按需求分组，**同一需求的用例在一个任务里** | REQ-001：5 万阈值两侧、恰好 5 万、0、非 CNY、金额未知、审批通过/驳回、非 pending 拒绝 |
| 通用质量 `quality` | 不属于某条需求、而是系统应普遍满足的属性：幂等、并发/重复提交、数据隔离与可重复、输入校验与错误码、接口契约 | 付款回调幂等、二次付款冲突、重置后可重复、未定义字段 422 |
| 回归/冒烟 `regression` | 已有能力的守护，按优先级或主链路挑选，跨需求 | P0 主链路：小额自动通过→付款；大额审批→付款 |

- 用例增加 `category`（默认 requirement）和可选 `quality_tags`；AI 生成用例和 AI 补全会填这两个字段，人可改。
- 策略生成规则：每条需求一个“需求验证”任务（不再按测试点拆成多个任务）；质量属性合成一个“通用质量”任务；另有一个“回归/冒烟”任务（P0）。
- 报告按分类分别统计通过率，并单列“跳过”。

### 4.4 顺带修复：边界用例不应跳过

`boundary`、`exception` 是功能测试的设计方法，应正常执行；只有 `performance`、`security`、`reliability` 等真正的非功能类型才跳过。报告通过率改为 `通过 /(通过+失败)` 并同时显示“跳过 N”，避免“100%”误导。这是小改动（约 0.5 天），建议不等方案决定先修（见问题 4）。

## 6 需要你决定的问题

1. **任务里的用例**：同意“任务只引用用例、缺口再生成用例草稿”吗？还是希望策略生成时直接为每个任务生成用例（会和已有用例重复，需要去重）？
2. **自动同步**：用例变为可执行后，是否自动加入规则匹配的任务（推荐，任务页可看到并手工排除），还是只在点“同步”时加入？
3. **分类边界**：输入校验/错误码类用例（如 TC-013 负金额/缺少币种返回 422）算“需求验证”还是“通用质量”？推荐：需求里写到的校验算需求验证，需求没写、系统通用的校验算通用质量。
4. **边界用例跳过的 bug**：是否先单独修（约 0.5 天，修后重跑任务会多执行 4 个用例，可能出现失败，例如阈值恰好 5 万的用例）？
